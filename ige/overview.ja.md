# IGE (Intent Guidance Engineering) 概要

## 1. はじめに

IGE（Intent Guidance Engineering：意図ガイダンス工学）は、ソフトウェア開発ライフサイクル（SDLC）において、PM（プロダクトマネージャー）の世界を支援するための工学体系です。

ソフトウェア開発において、意図（Intent）は人の頭の中にのみ存在します。

頭の中にあるアイデアや仮説、解決策の構想は、最初は曖昧で断片的です。IGEは、この頭の中の意図から要求書を起こし、実際の機能として設計してタスクに分解し、開発側（ISE）と健全に対話できる状態へ導きます。

---

## 2. PMのための工学としての IGE

ISEが「開発者をAIで支援する工学」であるのに対し、IGEは「PMをAIと要求工学で支援する工学」に位置づけられます。

```text
  [ PMの頭の中にある Intent ]
  ・なぜこれを作るのか（Why: 外部環境の課題、ユーザーのペイン、ビジネス目標など）
  ・何を解決したいのか（What: 解決仮説、提供価値のイメージ、実験構想）
               │
               ▼
  +--------------------------------------------------------------+
  |               IGE (Intent Guidance Engineering)              |
  |                                                              |
  |  1. 要求獲得・言語化 (Elicitation)                            |
  |     - 頭の中の暗黙知、前提条件、思い込みの明確化               |
  |  2. 要求分析・モデリング (Analysis & Modeling)                |
  |     - ゴール指向要求分析（Why -> What）、ユーザーストーリー     |
  |  3. 仕様化とタスク分解 (Specification & Decomposition)        |
  |     - 受け入れ基準 (Given-When-Then)、機能要件・非機能要件     |
  |     - 検証実験のスコープ設計と計測要件（何をもって判定するか） |
  |     - 開発者が着手可能な粒度のタスク定義                         |
  +--------------------------------------------------------------+
               │
               ▼
  [ 外部化された要求書・機能設計・タスク群 ]
               │
               ▼ (ODFによる調停・負荷確認)
  [ ISE（開発者）への受け渡し・実装へ ]
```

---

## 3. 要求工学（Requirements Engineering）の適用

IGEは、学術的な要求工学の諸原則をPMの実務に適用する体系です。

1. **ゴール指向要求分析（WhyからWhatへ）**  
   「このボタンを付けてほしい」といった表層的な要望にとどまらず、どのビジネスゴールやユーザー課題を解決するための機能かを論理的に分解します。
2. **受け入れ基準（Acceptance Criteria）の策定**  
   開発者が迷わず実装やテストを行えるよう、期待する振る舞いを明確に定義します。
3. **理解の乖離（Understanding Drift）の抑止**  
   顧客の要望とPMの認識の不一致による大きな手戻りを防ぐため、要求の前提をあらかじめ検証可能な形式に整理します。

---

## 4. ODFとの連携：開発現場を守るコミュニケーション

IGEが具体化した要求書やタスクは、開発現場（ISE）へ直接無制限に投入されるのではなく、必ずODF（Proxy）を経由して調停されます。

```text
       【 IGE (PM) 】                  【 ODF (Proxy) 】              【 ISE (開発者) 】
             │                                │                                │
             │── 1. 機能要求・タスク群の提案 ─>│                                │
             │                                │── 2. キャパシティ・負荷確認 ──>│
             │                                │<── 3. ベロシティ・工学的制約 ──│
             │<── 4. スコープ・優先順位の調停 ─│                                │
             │                                │── 5. 合意されたタスクの実装 ───>│
             ▼                                ▼                                ▼
```

ODFがタスク量と開発速度（ベロシティ）の釣り合いを監視するため、PMは開発現場を疲弊させることなく、優先度の高いタスクを着実に投入できます。また、ISE側からの「既存アーキテクチャへの影響が大きい」「例外系の考慮が足りない」といった工学的フィードバックをODFを介して受け止め、要求を柔軟に再調整します。

---

## 5. まとめ

- **対象**  
  PM（プロダクトマネージャー）の思考と業務プロセスを支援します。
- **本質**  
  人の頭の中にのみある意図を、明確な要求書、機能設計、タスク群へと外部化・具体化します。
- **連携**  
  具体化したタスクはODF（Proxy）を通じて開発側のキャパシティと調停され、開発者（ISE）へと安全に引き渡されます。
