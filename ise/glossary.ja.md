# 用語集

> Note: 本稿の問題意識、主要な概念、最終判断は筆者（人間）によるものです。一方で、文章の構成、表現の整理、下書きの生成にはAIの支援を受けています。最終的な内容の責任は筆者にあります。

この文書は、ISE関連文書で使う用語を整理するための用語集である。

ここに含まれる用語には、既存の一般用語、ソフトウェアエンジニアリング上の用語、近年のAI開発文脈の用語、筆者が本稿群で説明のために用いる独自の呼称が混在している。独自の呼称は、標準用語や広く合意された業界用語として提示するものではない。

## AI-DLC / AI-SDLC

AIをソフトウェア開発ライフサイクル全体に組み込もうとする考え方や取り組み。

要求、設計、実装、テスト、レビュー、運用、保守などの各段階でAIを使う。ただし、AIを導入しても、意図の定義、検証、同期、維持が自動的に解決されるわけではない。

## ADR

Architecture Decision Recordの略。

アーキテクチャ上の判断、採用理由、代替案、制約、影響を記録する文書。ISEでは、Whyや棄却案を保持する重要な成果物の一つとして扱う。

## As-Is

現在実際にそうなっている状態。

コード、テスト、実行時挙動、運用実態から比較的復元しやすい。一方で、As-Isだけでは「本来どうしたかったのか」はわからないことが多い。

## As-Intended

本来意図されていた状態。

なぜその判断が採用されたのか、どの代替案が捨てられたのか、どの制約が重視されたのかを含む。成果物に明示されていなければ、後から完全に復元することは難しい。

## Cure

ISEにおける保守・治癒の観点。

差分、負債、危険箇所、複雑度、テスト不足、境界違反、設計劣化に介入し、コードや成果物の健康度を回復する活動を指す。

## Drift

成果物間のズレ。

仕様、設計、コード、テスト、Issue、ADR、運用手順、人間の記憶が、同じ意図に接続されなくなることを含む。

## Eventual Consistency

結果整合性。

ISEでは、常に完全一致している状態を要求しない。一時的なズレは起こるが、放置せず、最終的に意図と成果物が収束する状態を目指す。

## Forward Sync

意図や仕様から、コード、テスト、運用などへ向かう同期。

```text
Intent / Spec -> Code / Test / Reality
```

従来の順方向開発と相性がよいが、現実の開発はForward Syncだけでは足りない。

## Harness Engineering

AIを制約、ツール、テスト、フィードバックループで囲い、暴走や場当たり的な生成を抑えるための考え方。

SDDの憲章、プロジェクトルール、テスト、CI、レビュー、静的解析などと近い役割を持つ。ただし、Harnessは意図そのものを代替しない。

## IDD

Intent-Driven Developmentの略として使われることがある考え方。

意図を中心にAIや開発プロセスを動かそうとする方向性。ただし、意図をどう外部化し、成果物群とどう同期し、ドリフトをどう検出するかは別途扱う必要がある。

## IGE

Intent Guidance Engineeringの略。

曖昧な要求、観測、痛み、不満、運用信号、市場信号などから、実装可能なintentやissueへ導くための考え方。

```text
IGE:
  vague signal / pain / request
    -> intent / issue / implementable direction
```

ISEが主に実装側の同期を扱うのに対し、IGEは上流の曖昧さを扱う。

## ISE

Intent-Synchronized Engineeringの略。日本語では、意図同期型エンジニアリング。

筆者が本稿群で提唱する呼称であり、既存の標準化された開発手法や広く合意された業界用語ではない。

ISEは、IntentとRealityを、複数の成果物を通じて継続的に同期するための実装側フレームワークである。

```text
ISE:
  accepted intent
    -> spec / design / code / test / docs / operation
```

## Intent

意図。

単なる気分や願望ではなく、システムをどうしたいのか、なぜそうしたいのか、何を優先するのか、何を捨てるのか、どの制約を守るのか、どのリスクを受け入れるのか、どの状態を正しいとみなすのか、という判断のまとまり。

## Intent Recovery

失われた意図、または明示されていない意図を、コード、テスト、運用実態、Issue、PR、コミットログ、古いドキュメント、人間の記憶から復元する作業。

重要だが理想状態ではない。復元できるのは主にAs-Isであり、As-Intendedの完全復元は難しい。

## Living Spec

生きた仕様。

固定された文書ではなく、Realityからの反作用を受けて更新され続ける仕様。ISEでは、SSoTを固定された石板ではなく、交渉によって更新されるLiving Specとして扱う。

## ODF

Orthogonal Dual-Frameworkの略。

IGEとISEを混ぜず、限定されたインターフェースで接続するための全体構造。

要求探索、価値判断、プロダクト判断と、実装側の意図同期を直交分離することで、コンテキストの混線を避ける。

## Provenance

情報の出所。

コードから得た事実、テストから得た期待、運用ログから得た現実、人間の記憶から得た背景、古いドキュメントから得た仮説は、同じ重みでは扱えない。ISEでは、情報の出所と信頼度を区別する。

## Reality

実際の現実。

コード、テスト、実行時の振る舞い、運用上の制約、既存システムの構造、ログ、障害、ユーザーの実際の使い方などを含む。

## Reverse Sync

コード、テスト、実行時挙動、運用、履歴から、仕様や意図へ戻す同期。

```text
Code / Test / Runtime / History -> As-Is knowledge -> Spec / Intent
```

既存システムでは頻繁に必要になる。ただし、Reverse Syncで復元できるのは主にAs-Isであり、As-Intendedを完全に復元することは難しい。

## SDD

Spec-Driven Developmentの略。

仕様を中心に置いて開発を進める考え方やツール群。AI時代には、仕様から実装を生成する手法として注目されている。ただし、既存システム、変更、ドリフト、逆方向の復元、成果物群の同期には課題が残る。

## SSoT

Single Source of Truthの略。

一般には「唯一の真実」と訳されることが多い。ISEでは、SSoTを絶対真理ではなく、現時点で採用された意図のスナップショット、すなわち交渉の決着として扱う。

## Vibe Coding

AIに大まかな意図や雰囲気を伝え、細部の設計や実装をAIの推論に委ねる開発スタイル。

高速に動くものを作れる一方で、意図、制約、判断理由、設計境界が明示されないままコードへ固定される危険がある。

## Vibe Management

筆者が現場で観測してきた問題を説明するための独自の呼称。

要求、制約、優先順位、判断理由が十分に言語化されないまま、雰囲気、圧力、期限、断片的な情報によって開発を進めようとする管理状態を指す。

## 意図の外部化

頭の中、会話、違和感、経験、暗黙知として存在する意図を、他者が実行・検証・反論・更新できる形式へ変換すること。

単なる文章化ではない。要求、仕様、設計、Issue、ADR、テスト、コードコメントなどへ変換し、成果物として扱えるようにすることを含む。

## 意図の変質

意図が単に忘れられるのではなく、時間経過、事後合理化、現在の理解、組織文脈によって別の説明へ置き換わること。

ISEでは、意図は失われるだけでなく変質するため、鮮明なうちに成果物へ同期する必要があると考える。

## 意図保持の減衰

意図が時間とともに鮮明さを失い、検索されにくくなり、別の説明へ再構成されやすくなる現象。

本稿群で説明のために使う整理であり、標準用語として提示するものではない。忘却曲線、記憶痕跡の減衰、Goal Activation / Goal Decay、アーキテクチャ知識の揮発などと接続できる。

## 情報のモザイク

筆者が現場で観測してきた問題を説明するための独自の呼称。

一つの情報空間の中に、信頼性、時制、意図、出所の異なる情報が混在し、外部から見てどれが現在の真実なのか判別しにくくなった状態。

## ソフトウェア考古学

既存システムの意味、意図、制約、現在の真実を、コード、テスト、ドキュメント、Issue、PR、コミットログ、運用記録、人間の記憶から発掘する作業。

単なる調査ではなく、矛盾する情報を読み分け、信頼度を見積もり、変更してよい範囲を判断する高度な知的作業である。

## ドキュメント・ドリフト

仕様書、設計書、README、運用手順、コメントなどが、実際のコードやシステムの挙動、現在の意図から乖離していくこと。

ISEでは、単なる文書更新漏れではなく、意図の接続性が失われる問題として扱う。

## 補装具としてのAI

AIを単なるコード生成器ではなく、人間の意図外部化を助ける補助装置として扱う考え方。

話すのが得意な人、書くのが得意な人、図で考える人、コードを書きながら考える人など、それぞれの得意・不得意をAIで補い、意図を文字化された成果物へ接続することを目指す。

## 理解負債

コードやシステムが存在していても、それを安全に理解し、変更し、説明できる知識が不足している状態。

技術的負債と相互に強化し合う。理解負債が大きいほど、変更前の調査、レビュー、オンボーディング、障害対応の負荷が増える。
