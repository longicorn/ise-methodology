## 1. 位置づけと目的

ISE（Intent Synchronized Engineering）は「意図」と「現実」の双方向同期を扱う抽象モデルである。
これを具体的な開発運用やツール（Nagi等）へ接続するための中間層として **Lane Model** を定義する。

- **ISE**: 意図と現実、差分、同期を捉える抽象理論。
- **Lane Model**: 同期の流れを有向グラフとして捉え、開発者が「いま何を行っているか」を意識的に操作するための概念層。
- **実装（Nagi等）**: Lane Modelを具体的な開発運用、コマンド、データ管理へ写像した具象システム。

Lane Modelは特定のコマンド構文やディレクトリ配置そのものを縛るものではなく、ソフトウェア開発のフローと作業コンテキストを捉える枠組みを提供する。

### 1.1 AIの利用有無に対するスタンス（アクターの中立性）

Lane Model は、AIエージェントの普及によってコードの生成・変更速度が跳ね上がり、現実が先行しやすい現代の開発環境を見据えたフローの再定義でもある。しかし、**モデル自体がAIの利用を前提としたり、強制したりするものではない**。

開発現場には、AIを積極的に取り入れたい開発者もいれば、品質・セキュリティ・理解度の観点からAIの自動生成を好まない（あるいは拒絶する）開発者も存在する。また、エディタの補完程度にAIを使う場合もあれば、特定Laneを人間に委ね、別LaneをAIとの協調で進める運用もある。

Lane Model では、あるLane（変換活動）の担い手が人間か、AIか、あるいは決定論的な自動化ツールかという「アクター（実行主体）」を直交する関心事として扱う。
- 「このLaneは品質責任を持つ人間が自らコードを書く」
- 「このLaneはAIが生成したドラフトを人間がレビューする」
- 「このLaneは静的解析ツールが機械的に抽出する」

このように、多様なスタンスを持つエンジニアがチームとして共存し、各Laneの責務や役割分担を柔軟に設計できることこそが、Lane ModelがISEから受け継いでいる重要な考え方である。

## 2. 道路の比喩と開発者のメンタルモデル

Lane Model の発想の根底には **「道路での移動」** の比喩がある。

人が道路を移動するとき、最終的な始点や終点（目的地）があり、その途中にいくつかの「中間目標（インターチェンジや中継地）」を設定し、それらをつなげたルートを想定して車を走らせる。  
そして運転中は、自分が今どの方向に向かっていて、次の目標地点へ行くためにどのレーンを走っているかを常に意識しているはずである。

ソフトウェア開発もこれと全く同じである。
- 最初から最後まで一本道で進む固定工程（Layer）ではない。
- 開発者は「いま自分は仕様からコードへ向かうレーンを走っている」「いまはコードから事実を整理するレーンに入っている」といった、**作業モードや変換コンテキストとしてのLane** を強く意識して作業している。

Lane Model は、この開発者の自然なメンタルモデルをグラフ理論の **有向グラフ（Directed Graph）** として形式化したものである。

## 3. Lane Model の基本構成要素

Lane Model は、以下の要素によって構成される。

```text
       Lane（有向Edge / 移動・変換そのもの）
[Node A] ----------------------------------> [Node B]
 (出発地/中間目標)                             (目的地/中間目標)

======= Route（中間目標をつなげた開発ルート） =======>
```

### 3.1 Direction（大きな同期方向）
開発全体の大きな潮流として、2つの方向を定義する。

- **Forward（順方向）**  
  `Intent → Spec → Code` と進む、通常の仕様化・実装開発を行う方向。
- **Reverse（逆方向）**  
  `Code → Spec` などのように、実装を解析・理解してその上位にあたる成果物を作る方向。
  コードからの復元には意図や判断理由などの情報の欠落が伴うため、実際には「Pre-Spec（暫定仕様）」のような位置づけになることが多い。これを人が読み解き・理解することで、最終的に上位の `Intent` にフィードバックを与えていく。  
  分かりやすい代表事例としては仕様書が存在しない「レガシーシステムへの適応（リバースエンジニアリング）」が挙げられるが、適用範囲はそれだけに留まらず、AI生成コードの仕様把握や既存機能の整理など多様な場面で用いられる。

### 3.2 Node（頂点：状態・成果物・中間目標）
同期の過程における中継地点、成果物、あるいは知識の状態を表す。

- 主に `Intent`、`Spec`、`Code` などがこれに当たる。
- 具体的なNodeの種類や粒度は、開発対象（Webアプリ、組み込み、インフラ等）やプロダクトによって異なるため、**Lane Model 自体は特定のNodeを固定的に義務付けない**。
- 実装側（Nagi等）においては、標準的なデフォルトのNodeセットを用意しつつ、ユーザーやプロジェクトが独自の中間成果物を容易に拡張・追加できる設計が望まれる。

### 3.3 Edge / Lane（有向辺：変換活動そのもの）
方向を持った Node 間をつなぐものであり、**いま移動している Lane（変換活動）そのもの** を表す。

- 例：`Spec → Code` の Edge であれば、それは「仕様をコードに落とし込む実装作業（Coding）」という Lane になる。
- 例：`Code → Observation / Fact` の Edge であれば、「コードを解析ツールで読み取って事実を抽出する」という Lane になる。
- 始点と終点を持ち、明確な向きを持つ。

### 3.4 Gate（通過点・判断点）
Gate は、Lane 上または Node 間の接続に設けられる通過点・判断点である。Lane の変換結果や次の Node への接続について、通過、保留、差し戻しなどを扱う。Gate は Lane Model における一般概念であり、特定のツールや評価方式を指さない。

- Gate は常に必須とは限らず、状況に応じて bypass できる。
- Gate で情報を確認し判断する過程では、情報が選択、省略、再解釈されることがある。Gate は接続を制御するだけでなく、Node 間で何が引き継がれるかにも影響しうる。
- Gate はツール上の明示的な機構に限らない。人が Intent を Document に表現する過程にも、意図を選び、言葉にし、読み手に伝える判断が含まれる。このため、頭の中の考えと文書の表現にずれが生じうる。
- Node は時間とともに変化する。同じ人でも、昨日の自分と今日の自分を異なる時点の Node として捉えられる。昨日作った Document を今日読み直したときに違和感が生じる場合、時点の異なる Node の状態に加え、それらを接続する過程での解釈や情報の変化が関係する。

Gate は、異なるフレームワークの境界にも、各フレームワークの内部にも置くことができる。どこに置くか、何を判断するか、bypass を許すかは、その接続の目的に応じて定める。

### 3.5 Route（経路）
目的を達成するために選択される、複数の Node と Lane の連なり。
開発者は目的に応じて必要な中間目標（Node）を設定し、それらを順次辿るルートを選択して進む。

### 3.6 Node/Edge構造と関係性に由来する負荷
Node と Edge の構造は、対象の状態や変換を表すだけでなく、Node 間の関係を把握・調整するときに生じる負荷を考える枠組みにもなりうる。

ブルックスの法則に関連して知られる `n(n−1)/2` は、n 個の要素がすべて相互に接続される場合の辺の数を表す（Fred Brooks, *The Mythical Man-Month*, §2.3）。チームのコミュニケーションでは、各人を Node、相互の連絡経路を Edge とみなせる。この式は完全グラフにおける辺の最大数であり、実際のチームが全員と同じ頻度・内容で連絡を取ることや、辺の数だけで調整負荷が決まることを意味しない。

同じ Node/Edge の見方を、人がソフトウェアを理解する場面にも広げられる可能性がある。たとえば、システムの構成要素や知識を Node、その間の依存関係や相互作用を Edge として表し、理解する人も Node として置くことで、人が構造を理解したり変更の影響を判断したりする際の関係をモデル化できる。そこから、追跡・解釈する関係が理解負荷に関わるという仮説を立てられる。この場合、人同士のコミュニケーションとシステム理解とでは、Edge の意味やコストの種類が異なる。

実際のグラフは疎であり、各 Edge の重みや重要度も一様ではない。また、人はシステム全体を常に把握するとは限らず、抽象化によって複数の Node をひとまとまりとして扱うこともある。そのため、`n(n−1)/2` を理解負荷の計算式として直接使うのではなく、Node 間の関係が負荷に関わる可能性を考える出発点として扱う。この拡張は、Lane Model の抽象化から導かれる仮説であり、実証された法則ではない。

## 4. 開発における操作と意識（実装への写像イメージ）

Lane Model を採用した実装（Nagi等）において、開発者がツールを操作する際の体験イメージは次のようになる。

開発者は、ツールに対して以下の要素を明示的・意識的に指定して作業を進める：

1. **Direction（どちらを向いているか）**
   いま進めたいのは Forward なのか、それとも Reverse なのか。
2. **向かう先の Node（どこへ行こうとしているか）**
   次は `Spec` を作るのか、`Code` を書くのか、それとも解析結果や知識をまとめるのか。
3. **対象領域と具体的な操作内容（その中で何を動かすか）**
   例えば「認証機能」を作っているのか、「Admin画面」を作っているのか。
   さらにその中でも「機能本体のコード実装」なのか、「テストコードの実装」なのか。

このように、**「Direction」「向かう先のNode」「対象と操作」** を開発者が明示的に指定してドライブできる環境を提供することで、人とAI（あるいは自動化ツール）が「いまどの文脈で、何を目指して作業しているのか」を完全に見失わずに同期を進めることができる。

## 5. 同期（Synchronization）との関係

ISEの根底にあるのは、「意図（Intent）」と「現実（Reality）」の間で継続的に同期を取り続けるという思想である。

ソフトウェア開発の現場では、仕様、コード、テスト、環境といった様々なNodeが独立して変化し、常に揺れ動いている。そのため、静的で不変の単一の真実（SSoT: Single Source of Truth）を固定的に維持し続けることは極めて困難である。
ISEにおいては、固定的な真実を求めるのではなく、揺れ動き続ける成果物や知識の間で合意を形成し、相互に影響を与え合いながら整合性を高めていく動的なプロセスとして同期を捉える。

- **`Forward` 方向の同期**
  意図（Intent）を起点として仕様（Spec）を整え、それを元に実装（Code）化していくことで、意図を現実（Reality）側へと同期させる。
- **`Reverse` 方向の同期**
  現実（Reality）であるコードや実行環境から得られた観測事実を吸い上げ、知識や暫定仕様（Pre-Spec）として構造化することで、意図（Intent）側へフィードバックし同期させる。

すべての活動は、最終的に意図と現実の一致（同期状態の前進）へと収束していく。
Lane Model は、この不断に揺れ動く同期のプロセスを人間（およびAI）が迷わずに理解し、今どの部分の整合性を進めているのかを意識的・確実に実行できるようにするための枠組みである。
