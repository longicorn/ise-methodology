## 1. 位置づけと目的

本リポジトリでは、ソフトウェア開発ライフサイクル（SDLC）を「Environment（環境）⇄ Intent（意図）⇄ Reality（現実・実装）」の3層の双方向同期として捉え、これを抽象化した体系としてODF、IGE、ISEを定義しています。
この抽象的なフレームワーク群を、具体的な開発運用やツール（Nagi等）へ接続するための中間層としてLane Modelを定義します。

- **ODF / IGE / ISE**: 環境、意図、現実の3層と、それらの同期・調停・要求展開を捉える抽象理論・SDLCフレームワーク群
- **Lane Model**: ODF / IGE / ISEの間および各フレームワーク内部のどこにでも適用され、すべての同期や変換の流れを有向グラフとして捉えて、開発者や各アクターが「いま何を行っているか」を意識的に操作するための概念層
- **実装（Nagi等）**: Lane Modelを具体的な開発運用、コマンド、データ管理へ写像した具象システム

Lane Modelは特定のコマンド構文やディレクトリ配置そのものを縛るものではなく、ソフトウェア開発のフローと作業コンテキストを捉える枠組みを提供します。

### 1.1 AIの利用有無に対するスタンス（アクターの中立性）

Lane Modelは、AIエージェントの普及によってコードの生成や変更の速度が上がり、現実が先行しやすい現代の開発環境を見据えたフローの再定義でもあります。ただし、モデル自体がAIの利用を前提としたり、強制したりするものではありません。

開発現場には、AIを積極的に取り入れたい開発者もいれば、品質やセキュリティ、理解度の観点からAIの自動生成を好まない（あるいは使わない）開発者もいます。また、エディタの補完程度にAIを使う場合もあれば、特定のLaneを人間に委ね、別のLaneをAIとの協調で進める運用もあります。

Lane Modelでは、あるLane（変換活動）の担い手が人間か、AIか、あるいは決定論的な自動化ツールかという「アクター（実行主体）」を直交する関心事として扱います。
- 「このLaneは品質責任を持つ人間が自らコードを書く」
- 「このLaneはAIが生成したドラフトを人間がレビューする」
- 「このLaneは静的解析ツールが機械的に抽出する」

多様なスタンスを持つエンジニアがチームとして共存し、各Laneの責務や役割分担を柔軟に設計できることこそが、Lane Modelが本フレームワーク群（ODF/IGE/ISE）から受け継いでいる基本的な考え方です。

## 2. 道路の比喩と開発者の意識

Lane Modelの発想の根底には「道路での移動」の比喩があります。

人が道路を移動するときは、最終的な出発地や目的地があり、その途中にいくつかの中間目標（インターチェンジや中継地）を設定し、それらをつなげたルートを想定して車を走らせます。運転中は、自分が今どの方向に向かっていて、次の目標地点へ行くためにどのレーンを走っているかを常に意識しています。

ソフトウェア開発もこれと同じです。最初から最後まで一本道で進む固定工程（Layer）ではありません。
開発者は「いま自分は仕様からコードへ向かうレーンを走っている」「いまはコードから事実を整理するレーンに入っている」といった、作業モードや変換コンテキストとしてのLaneを強く意識して作業を進めています。

Lane Modelは、こうした開発者の自然な捉え方をグラフ理論の有向グラフ（Directed Graph）として形式化したものです。

## 3. Lane Modelの基本構成要素

Lane Modelは、以下の要素で構成されます。

```text
       Lane（有向Edge / 移動・変換そのもの）
[Node A] ----------------------------------> [Node B]
 (出発地/中間目標)                             (目的地/中間目標)

======= Route（中間目標をつなげた開発ルート） =======>
```

### 3.1 Direction（大きな同期方向）
開発全体の大きな潮流として、2つの方向を定義します。

- **Forward（順方向）**  
  `Intent → Spec → Code` と進む、通常の仕様化や実装開発を行う方向です。
- **Reverse（逆方向）**  
  `Code → Spec` などのように、実装を解析・理解して上位の成果物を作る方向です。
  コードからの復元には意図や判断理由などの抜け落ちが伴うため、実際には「Pre-Spec（暫定仕様）」のような位置づけになることが多くなります。これを人が読み解いて理解することで、最終的に上位の `Intent` にフィードバックを返します。仕様書が存在しないレガシーシステムのリバースエンジニアリングをはじめ、AIが生成したコードの仕様把握や既存機能の整理など、幅広い場面で用いられます。

### 3.2 Node（頂点：状態・成果物・中間目標）
同期の過程における中継地点、成果物、あるいは知識の状態を表します。

- 主に `Intent`、`Spec`、`Code` などが該当します。
- 具体的なNodeの種類や粒度は、開発対象（Webアプリ、組み込み、インフラ等）やプロダクトによって異なるため、Lane Model自体は特定のNodeを固定的に義務付けません。
- 実装側（Nagi等）においては、標準的なデフォルトのNodeセットを用意しつつ、ユーザーやプロジェクトが独自の中間成果物を拡張・追加できる設計が望まれます。

### 3.3 Edge / Lane（有向辺：変換活動そのもの）
方向を持ったNode間をつなぐものであり、いま進めている変換活動そのものを表します。

- 例：`Spec → Code` のEdgeであれば、「仕様をコードに落とし込む実装作業（Coding）」というLaneになります。
- 例：`Code → Observation / Fact` のEdgeであれば、「コードを解析ツールで読み取って事実を抽出する」というLaneになります。
- 始点と終点を持ち、明確な向きを持ちます。

### 3.4 Gate（通過点・判断点）
Gateは、Lane上またはNode間の接続に設ける通過点・判断点です。Laneの変換結果や次のNodeへの接続について、通過、保留、差し戻しなどを扱います。GateはLane Modelにおける一般概念であり、特定のツールや評価方式を指しません。

- Gateは常に必須とは限らず、状況に応じて迂回（bypass）できます。
- Gateで情報を確認して判断する過程では、情報の選択、省略、再解釈が生じることがあります。Gateは接続を制御するだけでなく、Node間で何を引き継ぐかにも影響します。
- Gateはツール上の明示的な仕組みに限りません。人がIntentをDocumentに表現する過程にも、意図を選び、言葉にして読み手に伝える判断が含まれます。そのため、頭の中の考えと文書の表現にずれが生じることがあります。
- Nodeは時間とともに変化します。同じ人であっても、昨日の自分と今日の自分を異なる時点のNodeとして捉えられます。昨日作ったDocumentを今日読み直したときに違和感を覚える場合、時点の異なるNodeの状態に加え、それらをつなぐ過程での解釈や情報の変化が関係しています。

Gateは、異なるフレームワークの境界にも、各フレームワークの内部にも配置できます。どこに置くか、何を判断するか、迂回を許すかは、接続の目的に応じて定めます。

### 3.5 Route（経路）
目的を達成するために選択する、複数のNodeとLaneの連なりです。開発者は目的に応じて必要な中間目標（Node）を設定し、それらを順にたどるルートを選択して進みます。

### 3.6 Node/Edge構造と関係性に由来する負荷
NodeとEdgeの構造は、対象の状態や変換を表すだけでなく、Node間の関係を把握・調整するときに生じる負荷を考える枠組みにもなります。

ブルックスは、作業の各部分を相互に調整する必要があるとき、n個の作業単位間に最大 `n(n−1)/2` の通信経路が生じると論じています（Fred Brooks, *The Mythical Man-Month*, 第2章）。これは完全グラフの辺の数であり、常にすべての組合せが接続されることや、辺の数だけで調整負荷が決まることを示す式ではありません。

この見方をソフトウェアへ広げると、機能、仕様、コード、テストなどをNode、その間の依存、契約、変換、相互作用をEdgeとして表せます。ISEでは、意図に結び付く関係Edgeを通じてNode間の同期を保つ必要があります。すべてのNodeのあらゆる組合せを直接結ぶのではなく、必要な関係を明らかにし、そのEdgeを通じて影響を追うことが重要です。追跡・解釈する関係が増えるほど理解や調整の負荷も増えるという見方は、Lane Modelから導く仮説であり、ブルックスの式をそのままソフトウェア成果物の負荷計算に適用するものではありません。

現実のグラフは疎であり、Edgeごとに重要度も異なります。モジュール化、凝集度、結合度、依存方向、インターフェースの明確化は、Edgeを制御し、変更の影響や調整が必要な範囲を局所化するための設計手段です。モジュール分割を情報隠蔽に基づいて論じたParnasの研究や、タスクのモジュール性と調整負荷の関係を調べた実証研究は、この問題の背景にあります（[Parnas, 1972](https://doi.org/10.1145/361598.361623)、[Gomes and Joglekar, 2008](https://doi.org/10.1002/mde.1402)）。

### 3.7 機能間の関係と並行作業
機能単位、仕様単位、コード単位でそれぞれ整合していても、単位をまたぐ依存や共有前提が揃わず、統合時に問題が見つかることがあります。これはAI開発以前からある問題です。機能をNodeとして見るなら、機能内部の成果物とのEdgeに加え、機能間の依存、共有契約、相互作用も考慮する必要があります。機能単位で確認するGateも、関係する他のNodeとの整合性を確認することで、システム全体の同期に接続されます。

機能間の関係は、システム全体を完全に記述するものではなく、変更やGateで影響を調べるための手がかりです。NodeやEdgeは変化し、既知の関係がすべて登録されているとも限りません。それでも、関係をたどることで、どの成果物や機能まで確認すべきかを絞りやすくなります。

複数の開発者が並行して変更を進めると、PR同士が競合してマージできなくなったり、個別には成立している変更を統合した結果、機能間の仕様や振る舞いが食い違ったりすることがあります。これはAI以前から存在する問題です。競合には、同じ箇所を変更するテキスト上の競合と、Gitでは検出されない意味上の競合があります。意味上の競合をテストで検出する研究も、この問題を扱っています（[Detecting semantic conflicts with unit tests, 2024](https://doi.org/10.1016/j.jss.2024.112070)）。AIエージェントによるオーケストラ型開発や長期間の自律開発では、並行して進む変更の数や速度、継続時間が増し、既存の競合や機能間の前提ずれがより大きな問題になる可能性があります。

Thread設計の考え方は、この並行作業を捉える参考になります。ここでいう共有リソースをファイルだけでなく、仕様、API契約、データ形式、共有状態など意味を持つNodeとして捉えます。複数の作業がどのNodeを読み、どのNodeやEdgeを変更するかを考慮すれば、前提の更新、排他や順序付け、統合後の検証が必要な場所を特定しやすくなります。これはThreadの排他制御をそのまま適用するという意味ではなく、リソース競合を意味論的な依存関係として捉える類推です。

機能間の依存関係と、並行作業が同時に変更する対象は関連しますが、同一ではありません。前者は設計やGateで影響を追う関係であり、後者は作業の割当や同期のタイミングを調整する関係です。モジュール化や明確なインターフェースは、Edgeと変更の影響範囲を局所化する助けになりますが、意味上の整合性を自動的には保証しません。並行エージェントの協調を調べる研究では、個別にはタスクを実装できるコーディングエージェントでも、協働すると成功率が下がることが報告されています。失敗の要因としては、曖昧なコミュニケーション、合意した約束からの逸脱、他のエージェントの計画に関する誤った想定が挙げられています（[CooperBench, 2026](https://arxiv.org/abs/2601.13295)）。また、エージェント間の依存関係の充足を直接追う評価を提案するプレプリントもあります（[AsynCodeBench, 2026](https://arxiv.org/abs/2609.32662)）。

## 4. 開発における操作と意識（実装への写像イメージ）

Lane Modelを採用した実装（Nagi等）において、開発者がツールを操作する際の体験イメージは次のとおりです。

開発者は、ツールに対して以下の要素を明示的に指定して作業を進めます。

1. **Direction（どちらを向いているか）**  
   いま進めたいのはForwardなのか、それともReverseなのかを指定します。
2. **向かう先のNode（どこへ行こうとしているか）**  
   次は `Spec` を作るのか、`Code` を書くのか、あるいは解析結果や知識をまとめるのかを指定します。
3. **対象領域と具体的な操作内容（その中で何を動かすか）**  
   たとえば「認証機能」を作っているのか、「管理画面」を作っているのかを指定します。さらにその中でも「機能本体のコード実装」なのか、「テストコードの実装」なのかを明確にします。

このように、「Direction」「向かう先のNode」「対象と操作」を開発者が明示的に指定して操作できる環境を用意することで、人とAI（あるいは自動化ツール）が「いまどの文脈で、何を目指して作業しているのか」を見失わずに同期を進められます。

## 5. 同期（Synchronization）との関係

本フレームワーク群（Environment ⇄ Intent ⇄ Reality、ODF / IGE / ISE）の根底にあるのは、「環境」「意図」「現実」の間で継続的に同期を取り続けるという考え方です。

ソフトウェア開発の現場では、要求、仮説、仕様、コード、テスト、運用環境といった様々なNodeが独立して変化し、常に揺れ動いています。そのため、静的で不変の単一の真実（SSoT: Single Source of Truth）を固定的に維持し続けることは極めて困難です。
固定的な真実を求めるのではなく、揺れ動き続ける成果物や知識の間で合意を形成し、相互に影響を与え合いながら整合性を高めていく動的なプロセスとして同期を捉えます。

- **`Forward` 方向の同期**  
  環境課題や意図（Intent）を起点として要求や仕様（Spec）を整え、それを元に実装（Code）化していくなど、上位から下位へ同期を進めます。
- **`Reverse` 方向の同期**  
  現実（Reality）であるコードや実行環境、あるいは外部環境から得られた観測事実を吸い上げ、知識や暫定仕様（Pre-Spec）、あるいは更新された仮説として構造化することで、上位へフィードバックして同期させます。

すべての活動は、環境・意図・現実の整合性を高め、同期状態を前進させることにつながります。
Lane Modelは、この不断に揺れ動く全体の同期プロセスを人間やAIが迷わずに把握し、今どの部分の整合性を進めているのかを意識的かつ確実に実行するための枠組みです。
