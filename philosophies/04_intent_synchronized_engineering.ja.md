# Intent-Synchronized Engineering：意図の同期を中心に置くエンジニアリング

> Note: 本稿の問題意識、主要な概念、最終判断は筆者（人間）によるものです。一方で、文章の構成、表現の整理、下書きの生成にはAIの支援を受けています。最終的な内容の責任は筆者にあります。

前稿までで、ソフトウェア開発が抱え続けてきた問題を整理した。

ソフトウェアエンジニアリングは、要求、設計、実装、検証、保守を体系化してきた。プロジェクトマネジメントは、スコープ、スケジュール、コスト、リスク、ステークホルダーを管理してきた。アジャイルは、変化への適応と短いフィードバックループを重視した。AI時代には、Vibe Coding、SDD、IDD、Harness Engineering、AI-DLCといった新しい試みも登場した。

それでもなお、現場には同じ種類の問題が残っている。

ドキュメントはドリフトする。既存情報はモザイク化する。ソフトウェア考古学が必要になる。Vibe Managementによって曖昧な要求が流れ込む。AIはコード生成を高速化するが、意図の定義、検証、維持までは自動的に解決しない。

この一連の問題を考える中で、筆者がたどり着いた最も小さく、しかし確かな発見がある。

それは、意図の同期こそが重要である、という点だ。

本稿では、この発見を中心に、筆者が Intent-Synchronized Engineering（ISE: 意図同期型エンジニアリング）と呼ぶ開発上の考え方を提唱する。

なお、Intent-Synchronized Engineering / ISE は、筆者が本稿で用いるために定義する呼称であり、既存の標準化された開発手法や、広く合意された業界用語ではない。また、特定のツールや実装を指すものでもない。実装はあくまで実装であり、本稿で扱う中心は「意図と成果物を同期する」という考え方である。

## 1. 発見: 重要なのは「意図の同期」である

ソフトウェア開発では、さまざまな成果物が作られる。

要求、仕様、設計、コード、テスト、Issue、Pull Request、ADR、運用手順、障害記録、リリースノート、コメント、コミットログ。

これらは別々の形式を持ち、別々の場所に保存され、別々のタイミングで更新される。しかし本来、それらは同じ意図に接続されていなければならない。

ここでいう意図とは、単なる気分や願望ではない。

意図とは、システムをどうしたいのか、なぜそうしたいのか、何を優先するのか、何を捨てるのか、どの制約を守るのか、どのリスクを受け入れるのか、どの状態を正しいとみなすのか、という判断のまとまりである。

コードには、現在の振る舞いが残る。テストには、期待される振る舞いの一部が残る。仕様書には、作るべきものが残る。ADRには、判断理由が残る。Issueには、変更要求が残る。運用記録には、現実の制約が残る。

しかし、どれか一つだけで意図全体を保持することは難しい。

コードだけでは、なぜそうしたのかが残りにくい。仕様書だけでは、実装中に変わった判断が残りにくい。テストだけでは、価値判断や棄却案が残りにくい。Issueだけでは、実装後の現実が残りにくい。

したがって、どの成果物を唯一の真実とみなすかよりも、成果物群が共通の意図に同期され続けているかが重要になる。

## 2. ISEの定義

Intent-Synchronized Engineering（ISE）とは、意図と成果物の継続的な同期を中心に置くエンジニアリングの考え方である。

より短く言えば、ISEは次のように定義できる。

```text
ISE = Intent と Reality を、複数の成果物を通じて継続的に同期するための実装側フレームワーク
```

ここでいうIntentは、採用された意図、判断理由、制約、トレードオフ、未確定事項、棄却された選択肢を含む。

Realityは、実際のコード、テスト、実行時の振る舞い、運用上の現実、既存システムの制約を含む。

成果物は、その間を媒介する。

```text
Intent
  -> requirements / design / ADR / issue / tests / code / operations
  -> Reality
```

ISEの目的は、成果物を大量に作ることではない。ドキュメントを増やすことでもない。AIにコードを書かせることでもない。

目的は、意図が失われず、成果物間で矛盾しない状態を保つことである。

## 3. SSoTは絶対真理ではなく、交渉の決着である

ISEでは、SSoT（Single Source of Truth）という言葉を慎重に扱う必要がある。

一般には、SSoTは「唯一の真実」と訳される。しかし、ソフトウェア開発において真実は自明ではない。

同じ機能に対しても、複数の正当な意図が存在する。

たとえば認証機能であれば、セキュリティ担当は安全性を重視する。UX担当は使いやすさを重視する。ビジネス側は行動分析やコンバージョンを重視する。法務やコンプライアンスは規制要件を重視する。

これらはどれか一つだけが正しく、他が間違っているわけではない。意図は本来的に複数であり、しばしば競合する。

したがって、ISEにおけるSSoTは「世界に一つだけ存在する絶対的な正解」ではない。

それは、現時点でどの意図を採用するかについての交渉の決着である。

```text
SSoT = 現時点で採用された意図のスナップショット
```

この理解は実務上欠かせない。

仕様書や設計書を絶対視すると、実装中に見つかった新しい事実や、運用から返ってきた現実を無視しやすくなる。一方で、コードだけを絶対視すると、過去の判断理由や棄却された選択肢が消えてしまう。

ISEでは、SSoTを固定された石板と見なさず、交渉によって更新されるLiving Specとして扱う。

## 4. 同期は順方向だけではない

従来の開発手法は、多くの場合、要求から設計へ、設計から実装へ、実装からテストへ、という順方向の流れを基本にしてきた。

この流れは重要である。意図を先に外部化し、それに基づいて実装することは、今でも有効である。

しかし、現実の開発は順方向だけでは進まない。

既存システムから仕様を復元することがある。コードを書いて初めて設計の問題に気づくことがある。テストを書いて初めて仕様の曖昧さが見えることがある。運用中の障害から新しい制約が見つかることがある。小さな修正から、過去の設計意図との衝突が露出することがある。

つまり、意図と現実の関係は双方向である。

```text
Forward Sync:
  Intent / Spec -> Code / Test / Reality

Reverse Sync:
  Code / Test / Runtime / History -> As-Is事実 / 構造メトリクス -> Spec / Intent / ガバナンス
```

ISEでは、順方向と逆方向のどちらか一方のみを正解としない。

どの方向から始めたかに関わらず、継続的に意図と成果物が同期され、システムが保守可能に保たれているかが重要である。

従来のソフトウェア工学や昨今の仕様駆動開発（Spec-Driven Development）の議論では、「仕様からコードを生成する」という順方向（Forward Sync）に偏りがちであった。また、Reverse Syncが語られる場合でも、ドキュメントの失われたレガシーシステムの救済という狭い文脈にとどまることが多かった。

しかしISEにおけるReverse Syncは、ソフトウェアのライフサイクル全般を支える以下の3つの目的を持つ。

1. Legacy Recovery（失われた意図の救済）: ドキュメントが存在しない、あるいは形骸化したコードベースから、As-Isの振る舞い、業務ルール、設計根拠を発掘・再言語化し、人間による理解やモダナイゼーションを可能にする。
2. Drift Detection（意図と実装の乖離検証）: 実際のコードから仕様を客観的に再抽出し、既存のLiving Specと意味的・機械的に突合することで、意図しない逸脱、仕様書の更新漏れ、AIによるハルシネーションを検知・抑止する。
3. Entropy Control（複雑性の制御と構造ガバナンス）: コードの循環的・認知的複雑度、結合度、モジュール境界、依存関係の劣化を計測・監視し、開発に伴うエントロピーの増大を防ぎ、人間とAIが認知的に維持・推論可能な単位に保つ。

Drift DetectionとEntropy Controlがなければ、継続的な開発（特にAIによって加速された開発）は、人間もAIも安全に扱えないカオスへと必然的に突き進むことになる。

ただし、これは「順序は完全にどうでもよい」という意味ではない。意図は時間とともに揮発し、変質する。特に、人間の頭の中にある意図は最も失われやすい。したがって、意図が鮮明なうちに外部化し、成果物へ接続することが重要になる。

この背景については、認知負荷、記憶の再構成、共通基盤、意図保持の減衰という観点から、補論「[ドキュメント・ドリフトと意図の劣化](foundations/01_document_drift_and_intent_decay.ja.md)」で整理する。

AIは、この同期コストを大きく下げる。

開発者が実装直後にAIへ意図を説明すれば、AIは仕様、ADR、テスト観点、レビュー観点へ変換できる。既存コードをAIに読ませれば、As-Isの事実を整理できる。差分をAIに見せれば、どの意図が変わった可能性があるかを問い返せる。

AIによって、意図が失われる前に同期することが現実的になった。

## 5. 作成主体を固定しない

ISEでは、成果物を誰が作ったかだけで正しさを判断しない。

人間が仕様を書き、AIがコードを書く場合もある。AIが既存コードを読み、ドキュメントの下書きを作る場合もある。人間が直接コードを書き、AIが後からテストや設計メモを整理する場合もある。AIが提案し、人間が採用・修正・却下する場合もある。

関心の中心は、作成主体ではなく同期状態にある。

```text
誰が作ったか:
  human / AI / human + AI

本当に問うべきこと:
  その成果物は採用された意図と合っているか
  他の成果物と矛盾していないか
  判断理由と制約が失われていないか
```

この考え方により、開発主体の境界は柔軟になる。

ある人が実装してもよい。別の人が実装してもよい。AIが実装してもよい。人間とAIが協調してもよい。

ただし、これは「誰が作っても同じ」という意味ではない。

熟練した開発者が書くべきコードはある。設計判断、責務境界、性能、並行性、セキュリティ、長期的な保守性が重要な領域では、人間の経験と判断がAIを大きく上回ることがある。そのような領域では、人間が設計し、人間が実装し、AIは補助やレビューに回る方がよい場合がある。

一方で、すべての作業を熟練者が手で行う必要もない。定型的な実装、テストの下書き、ドキュメントの整理、既存コードの説明、リファクタリング候補の列挙などは、AIに任せたり、AIに補助させたりできる。

経験の浅い開発者にとっても、AIは単なる代替にとどまらず、心強い補助者になりうる。AIが設計意図を説明し、レビュー観点を提示し、既存コードの読み方を助けることで、経験の短さを補える場面がある。

つまり、ISEは人間を不要にする考え方ではない。人間の判断をAIで置き換えるための考え方でもない。むしろ、人間が判断すべき領域と、AIに委譲・補助させてよい領域を分けやすくするための考え方である。

ただし、それが可能になる条件がある。

意図が外部化され、成果物と同期されていることである。

意図が同期されていなければ、誰が開発しても危険である。熟練者であっても推測に頼ることになる。AIであれば、さらに高速に誤った前提をコードへ固定する。

逆に、意図が同期されていれば、作成者の違いは相対的に小さくなる。人間もAIも、同じ意図に向かって成果物を更新できるからである。

## 6. ISEの主要な特徴

ISEの特徴は、いくつかの観点に分けて整理できる。

### 継続的アライメント

ISEは、仕様、設計、コード、テスト、運用、判断履歴を一度だけ揃えるものではない。

開発中、レビュー中、運用中、保守中に、それらを継続的に揃える。

一時的なズレは起こる。実装が先行することもある。障害対応でコードが先に変わることもある。ズレが発生しない幻想を持つのではなく、ズレを検出し、交渉し、再同期することが肝心である。

### 双方向同期

ISEでは、仕様からコードへのForward Syncだけでなく、コードや実行時の現実から仕様、知識、および構造ガバナンスへとフィードバックするReverse Syncも必要である。

既存システムが存在し、コードベースが進化し続ける限り、Reverse Syncは例外的な作業ではない。むしろ現場において、Reverse Syncは以下の3つの目的を担う継続的なガバナンス・エンジンとして機能する。

1. Legacy Recovery: ドキュメントが存在しないレガシーコードから意味、業務ロジック、運用の現実を再構築し、理解と保守を可能にする。
2. Drift Detection: 実際のコードから仕様を継続的に抽出し、Living Specと突合することで、意図しない逸脱、仕様書の陳腐化、実装の暴走を可視化する。
3. Entropy Control: 構造的な複雑度、認知負荷、依存グラフの劣化、アーキテクチャ境界の侵害を継続的に監視・是正する。

ただし、Reverse Syncは万能ではない。コードから直接復元できるのは主にAs-Isの現実であり、開発当初のAs-Intendedな判断理由を完全に復元することは難しい。そのため、Reverse SyncはForward Syncやネゴシエーション・ループと連携して初めて真価を発揮する。

### 認知負荷の管理とエントロピー制御（Entropy Control）

ISEでは、人間にもAIにも認知限界があることを前提にする。

人間は巨大なコードベース全体を常に把握できない。AIも巨大なコンテキストを渡されれば、重要な情報を見落としたり、ハルシネーションを起こしたり、無関係な情報に引きずられたりする。特にAIによって実装速度が加速する環境では、コードのエントロピーは従来以上の速度で増大する。

そのため、ISEにおいてエントロピー制御（Entropy Control）は第一級のエンジニアリング課題である。機能、ドメイン、サブシステム、変更単位、責務境界ごとに、必要な意図と成果物を局所化し、対象範囲を小さく保つことが極めて重要になる。

これは単なるドキュメント分割ではない。Reverse Syncを通じて認知的複雑度、循環的複雑度、結合度、循環依存などのメトリクスを監視し、システム設計そのものを人間とAIが局所的に理解・変更・検証できる健全な単位に保ち続けるということである。

局所的に推論できる構造を維持することで、人間とAIの双方が認知的破綻を招くことなく、安全に変更を継続できる。

### 意図の救済とレガシーの保全（Legacy Recovery）

ISEでは、既存コードや運用実態から意図を復元する作業をLegacy Recoveryとして位置づける。しかし、それはあらゆる開発が目指すべき日常の理想状態ではなく、意図が失われた状態への救済・対応でもある。

コードから復元できるのは、主に現在の振る舞い（As-Is）である。

なぜ本来その判断が採用されたのか、どの案が棄却されたのか、誰がどのトレードオフを重視したのか、実装中に意図がどう変形したのかは、コードの構文だけからは完全には復元できない。

したがって、Legacy Recoveryはレガシー資産に対する極めて重要な生命線であるが、ISEの日常戦略としては、完全に意図が失われてから大規模に復元することに頼るのではなく、Drift DetectionとEntropy Controlを小さく継続的に回し、そもそも意図や構造が腐敗しない状態を維持することを目指す。

### 補装具としてのAI

ISEにおけるAIは、単なるコード生成器ではない。人間の意図外部化を助ける補装具である。

人によって苦手な変換ステップは異なる。意図を文章にするのが苦手な人もいる。仕様をコードに落とすのが苦手な人もいる。コードから設計を説明するのが苦手な人もいる。レビュー観点を言語化するのが苦手な人もいる。

AIは、その弱いステップを補うことができる。質問して意図を引き出す。断片メモを構造化する。コード差分から設計意図を推定する。仕様を実装案へ変換する。会話をADRやIssueへ変換する。古いドキュメントと現在のコードの差分を整理する。

この意味で、AIは人間を置き換えるというより、人間ごとの認知的な弱点を補い、意図が欠落しやすい箇所を支える存在である。

ただし、AIが人間の判断を不要にするわけではない。AIは候補を作れる。差分を見つけられる。説明を整えられる。しかし、何を採用し、何を捨て、どの責任を引き受けるかは、人間が決めなければならない。

### ネゴシエーション・ループ

同期は自動変換だけでは成立しない。

ドキュメントとコードがズレたとき、それはコードのバグかもしれない。仕様変更かもしれない。古い仕様の残骸かもしれない。運用上の暫定対応かもしれない。

したがって、ズレを検出した後には判断が必要になる。

ISEでは、この判断をネゴシエーション・ループとして捉える。

```text
Drift
  -> Analyze
  -> Compare
  -> Human judgment
  -> Update Intent or Reality
  -> Resync
```

AIは差分の検出、候補の整理、影響範囲の推定、更新案の作成を支援できる。しかし、何を採用するか、何を捨てるか、どのリスクを受け入れるかは、最終的には人間の判断である。

### Eventual Consistency

ISEは、常に完全一致している状態を要求しない。

現実の開発では、一時的な不整合は避けられない。重要なのは、それを放置しないことである。

短期的なズレを許容しつつ、最終的に意図と成果物が収束する状態を目指す。この意味で、ISEは結果整合性を前提にする。

### Provenanceと信頼度

情報のモザイクを扱うには、情報の出所と信頼度を落としてはいけない。

コードから得た事実、テストから得た期待、運用ログから得た現実、人間の記憶から得た背景、古いドキュメントから得た仮説は、同じ重みで扱うべきではない。

ISEでは、情報を単にまとめるにとどまらず、どこから来た情報なのか、どの程度信頼できるのか、現在のRealityと照合済みなのかを区別する必要がある。

### 保守を通じた健全性の回復

同期は、ドキュメントとコードを揃えるだけではない。

差分、負債、危険箇所、複雑度、テスト不足、境界違反、設計劣化に介入することも含む。

コードの健康度を確認し、必要に応じてリファクタリングし、設計を回復し、テストを補い、負債を返済する。このような保守活動も、意図とRealityを同期させるための重要な一部である。

## 7. 意図は実装中にも生まれる

意図は、最初に完全に定義されるものではない。

実装を始めて初めてわかることがある。コードを書きながら、よりよい設計に気づくことがある。テストを書いて、最初の仕様が曖昧だったことに気づくことがある。運用して、想定していなかった制約が現れることがある。

つまり、実装は単なる意図の実行ではない。実装そのものが新しい意図を生むことがある。

このとき、新しく生まれた意図を失わないことが肝心である。

多くの場合、開発者は「今、新しい意図が生まれた」と明確には自覚しない。実装中に自然に判断し、コードを変え、次の問題へ進む。その瞬間のWhyは、時間とともに急速に薄れていく。

ISEは、この現象に対して、同期コストを下げることで対処する。

新しい判断が生まれたら、すぐに記録できる。コード差分からAIが問い返せる。PR単位で、なぜそう変えたのかを整理できる。実装後に、設計や仕様へ戻せる。

完全な自動検出は難しい。しかし、同期の摩擦を下げれば、意図が失われる前に捕まえやすくなる。

## 8. ISEが減らすもの

ISEがうまく機能すると、次のような負荷を減らせる。

- ドキュメント・ドリフト
- 仕様と実装の認識違い
- なぜそうしたのかを探す時間
- オンボーディング時の認知負荷
- レビュー時の過剰な確認
- 「そういう意味だと思っていた」による手戻り
- 属人化した知識への依存
- ソフトウェア考古学の頻度と難易度
- AIによる場当たり実装の蓄積

これは、すべての会議や調整を消すという意味ではない。

むしろ、意図の非同期によって発生していた不要な確認、過剰な説明、認識違い、手戻りを減らすという意味である。

## 9. ISEが解かないこと

ISEは万能ではない。

ISEが扱うのは、主に定義済みの意図を、設計、コード、テスト、ドキュメント、運用へ同期することである。

したがって、次の問題はISE単体の責務ではない。

### 意図そのものが存在しない状態

「いい感じにしてほしい」「競合がやっているから作ってほしい」「とにかく早く出してほしい」のように、要求、制約、優先順位、成功条件が定義されていない状態では、ISEは十分に機能しない。

ISEは意図を同期できるが、存在しない意図を勝手に決定するものではない。

曖昧な要求から実装可能な意図を作る問題は、IGEの領域である。

### 価値判断と責任引受け

何を優先するか。何を捨てるか。どのリスクを今受け入れるか。誰の都合をどこまで通すか。不完全な情報の中でどこで決めるか。

これらは同期の範疇ではなく、価値判断と責任引受けの問題である。

ISEは、それらの判断が行われた後に、その判断を成果物へ同期することを支援できる。しかし、判断そのものを代替するものではない。

### 納期、見積もり、スケジュール管理

ISEは納期管理の手法ではない。

見積もり、スケジュール、リソース配分、契約、予算、組織上の都合は、プロジェクトマネジメントの領域である。

ISEは、開発を透明にし、意図と現実のズレを見えやすくすることで、見積もりや判断の材料を改善することはできる。しかし、納期を保証するものではない。

ここを混同すると、ISEは「より速く作らせるための管理の道具」として誤用される。これは避けるべきである。

### マネジメント側の曖昧さ

Vibe Managementは、ISEの外側にある問題である。

マネジメント側が意図を言語化しない、責任を引き受けない、未確定論点を隠す、政治的制約を明示しない、納期だけを押し込む。このような状態では、ISEはむしろ問題を可視化する。

可視化された問題をどう扱うかは、IGEおよびODFの領域である。

## 10. なぜIGEとODFが必要になるのか

ISEは、意図があることを前提にする。

しかし現実には、意図は最初から明確ではない。市場、顧客、運用、営業、サポート、開発者の違和感、ログ、メトリクス、障害、競合調査など、断片的なシグナルの中から意図候補を見つけなければならない。

この領域は、ISEではなくIGEが扱うべきである。

```text
IGE:
  曖昧な要求・signal -> 実装可能な intent / issue

ISE:
  定義済み intent -> spec / code / test / docs / operation への同期
```

両者を混ぜると危険である。

要求探索と実装同期を一つの巨大なプロセスや一つのAIに押し込むと、コンテキストが汚染され、判断軸が曖昧になる。ビジネス上の都合とエンジニアリング上の制約が混線し、結果として、曖昧な要求がきれいな仕様の形で下流へ押し込まれる。

そのため、IGEとISEは分離し、限定されたインターフェースで接続する必要がある。

この全体構造がODFである。

ODFは、要求定義と実装同期を直交分離し、Issue、Living Spec、SSoT、runtime feedback、pain point、drift signalなどを通じて接続するための考え方である。

## 11. ISEの誤用と劣化

ISEは、誤用されると別の問題を生む。

たとえば、ISEを「人間を同期の部品にする仕組み」として使うと、開発者の思索を削る。すべての判断を即座に文書化させ、余白を奪い、違和感や異議申し立てを減らしてしまう。

ISEを「納期を守るためにAIで開発速度を上げる仕組み」として使うと、結局は従来の速度偏重を強化するだけになる。

ISEを「ドキュメントを増やす仕組み」として使うと、形式的な文書だけが増え、意図の同期という核心が失われる。

ISEを「仕様に従わせる仕組み」として使うと、現実からの反作用が消える。実装中に見つかった事実、運用から返ってきた制約、開発者の違和感が上流へ戻らなくなる。

ISEには、反作用の権利が必要である。

開発側は、仕様の削減、再設計、保留、異議、リスクの提示を返せなければならない。そうでなければ、ISEは同期ではなく押し込みになる。

## 12. まとめ: ISEは「意図を失わないための実装側フレームワーク」である

ISEの核心は単純である。

意図の同期こそが重要である。

AI時代において、コードを書く速度は劇的に上がった。しかし、何を作るべきか、なぜそうするのか、どの制約を守るのか、何を捨てたのか、どの判断を採用したのかが失われれば、速く作れることはむしろ危険になる。

ISEは、コード、テスト、ドキュメント、仕様、運用、判断履歴を、共通の意図へ同期し続けるための考え方である。

それにより、人間が開発しても、AIが開発しても、人間とAIが協調しても、成果物が同じ意図に向かって更新される状態を目指す。

ただし、ISEは意図を魔法のように生み出すものではない。納期を保証するものでもない。マネジメント側の曖昧さを吸収するものでもない。

曖昧な要求から意図を作るにはIGEが必要である。IGEとISEを混ぜずに接続するにはODFが必要である。

次稿では、ISEが扱わない上流の問題、すなわち曖昧な要求やVibe Managementをどう扱うか、そしてIGEとODFがなぜ必要になるのかを整理する。
