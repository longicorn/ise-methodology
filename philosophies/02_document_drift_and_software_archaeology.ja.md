# ドキュメント・ドリフトとソフトウェア考古学：現場を苦しめてきた情報のモザイク

> Note: 本稿の問題意識、主要な概念、最終判断は筆者（人間）によるものです。一方で、文章の構成、表現の整理、下書きの生成にはAIの支援を受けています。最終的な内容の責任は筆者にあります。

前稿では、ソフトウェアエンジニアリングがどのように発展してきたのかを整理した。要求、設計、実装、検証、保守を体系化する標準。品質を扱うためのモデル。プロジェクトを管理するための知識体系。反復、フィードバック、変化への適応を重視するアジャイル。

それらはすべて、ソフトウェア開発をよりよく扱うための重要な知的資産である。

しかし、現実の開発現場では、それでもなお多くの課題が残り続けている。特に深刻なのは、実装に着手する以前に、そもそも「今このシステムは何なのか」「何が正しい情報なのか」「なぜこうなっているのか」を復元しなければならない状況である。

現場の開発者は、日常的に仕様書、設計書、コード、テスト、Issue、Pull Request、コミットログ、Slack、会議メモ、運用手順、そして人間の記憶を掘り起こす。古い記録と現在のコードを照合し、矛盾する情報を読み分け、失われた意図を推測し、変更してよい範囲を見極める。

これは単なる「調査」ではない。むしろ、ソフトウェア考古学と呼ぶべき作業である。

本稿では、ドキュメント・ドリフト、情報のモザイク、Vibe Management、技術的負債、理解負債がどのように絡み合い、現場の開発を難しくしてきたのかを整理する。

なお、本稿で用いる「情報のモザイク」「モザイク化」「Vibe Management」は、筆者が現場で観測してきた問題を説明するための独自の呼称である。既存の標準用語や広く合意された学術用語として提示しているわけではない。

## 1. 開発現場では「実装前の発掘」が常態化している

開発現場で新しい機能を追加したり、既存機能を修正したりするとき、開発者が最初に行うのは実装ではないことが多い。

まず、対象の機能が現在どう動いているのかを確認する。仕様書を探す。設計書を読む。関連するコードを追う。テストを見る。過去のIssueやPull Requestを探す。コミットログを確認する。運用手順や障害対応の記録を読む。必要であれば、当時を知る人に聞く。

このとき、情報は一枚岩ではない。

仕様書にはAと書いてあるが、コードはBになっている。テストはCを前提にしている。過去のIssueではDという判断がされている。SlackにはEという補足が残っている。運用ではFという回避策が使われている。

開発者は、これらを単に読むだけではない。どれが現在も正しいのか、どれが過去の遺物なのか、どれが願望なのか、どれが暫定対応なのかを判断しなければならない。

この作業は、ソフトウェア考古学に近い。

ただし、通常の考古学と違い、対象は静的な遺跡ではない。現在も動いているプロダクトであり、今も変更され続けているシステムである。調査している間にも、別のチームがコードを変更し、別のIssueが作られ、運用上の新しい制約が生まれる。

開発者は、動き続ける遺跡を発掘しながら、その上に新しい構造物を建てているようなものである。

## 2. ドキュメント・ドリフトは単なる文書更新漏れではない

この状況の背景にある代表的な問題が、ドキュメント・ドリフトである。

ドキュメント・ドリフトとは、仕様書、設計書、README、運用手順、アーキテクチャ文書などが、実際のコードやシステムの挙動から乖離していく現象を指す。

これは一見すると、単なる文書更新漏れに見える。しかし実際には、より深い問題を含んでいる。

ドキュメントには、単に「何をするか」だけでなく、「なぜそうするのか」「どの前提でそう判断したのか」「どの制約を重視したのか」「何をやらないと決めたのか」が含まれていることがある。コードが変更されても、これらの文脈が更新されなければ、ドキュメントは現在の実態とズレるだけでなく、過去の意図を誤って伝える危険な情報になる。

さらに、ドリフトは一方向にだけ起きるわけではない。

コードが先に進み、ドキュメントが置き去りになることもある。逆に、ドキュメント上では将来構想が書かれているが、実装はまだ存在しないこともある。古い設計判断が残り続け、新しい設計判断と混在することもある。運用上の回避策が事実上の仕様になっているのに、正式な仕様には反映されていないこともある。

つまり、ドキュメント・ドリフトは「文書が古い」という単純な問題ではない。それは、コード、テスト、仕様、設計、運用、意思決定の間で、現在の真実が分散し、互いにズレていく問題である。

一度ドリフトしたドキュメントは、読まれなくなる。読まれないドキュメントは、更新されなくなる。更新されないドキュメントは、さらに信頼を失う。

この循環に入ると、組織は次第に「コードを読めばわかる」という状態へ追い込まれる。しかし、コードを読めばすべてがわかるわけではない。コードからわかるのは、主に現在の振る舞いと構造である。過去の判断理由、棄却された案、政治的な制約、顧客との合意、将来の変更余地までは、コードだけでは復元しにくい。

## 3. 情報のモザイク

ドキュメント・ドリフトが進むと、情報空間はモザイク化する。

情報のモザイクとは、一つの情報空間の中に、信頼性、時制、意図、出所の異なる情報が混在し、外部から見てどれが現在の真実なのか判別しにくくなった状態である。

Notion、Confluence、Google Drive、GitHub Wiki、README、Issue、Pull Request、Slack、メール、会議メモ。多くの組織は、これらを使って情報を蓄積している。しかし、情報が同じ場所にあることと、同じ信頼性を持つことは違う。

同じワークスペースの中に、現在も正しい仕様、すでに廃止された設計方針、誰かの将来構想、途中で頓挫した機能のメモ、個人的な作業ログ、誤解に基づく記録、営業資料、障害時の暫定対応が並んでいる。

これらはすべて「情報」ではある。しかし、同じ種類の情報ではない。

モザイク状態では、少なくとも次のような情報が混在する。

| 種類 | 説明 |
|---|---|
| 現在の真実 | 現在の実装、運用、合意と一致している情報 |
| 過去の真実 | かつては正しかったが、現在は陳腐化した情報 |
| 未来像・願望 | 実現したい構想や計画だが、現時点の実装とは一致しない情報 |
| 暫定対応 | 障害対応や納期都合で一時的に採用された回避策 |
| 個人的な記録 | 作業ログ、メモ、思考途中の断片 |
| ノイズ | 現在の開発判断には直接使えない周辺情報 |
| 誤った情報 | 記録時点からすでに事実でなかった情報 |
| 残骸 | 中止された計画、消えた機能、未完了の設計の名残 |

これらは悪意によって生まれるわけではない、という点が重要である。

多くの場合、誰かはその時点で正しい情報を書こうとしている。あるいは、その時点では確かに正しかった。しかし、システムが変わり、要求が変わり、組織が変わり、文脈が失われる。結果として、情報空間はまだらになる。

この状態では、開発者は情報を読むだけでは足りない。情報を分類し、信頼度を見積もり、現在のコードや運用と照合しなければならない。

つまり、情報のモザイクは、開発者に追加の認知作業を要求する。

### 3.1 High-ContextとLow-Contextの混濁

本来、仕様ドキュメントとモザイク情報は役割が異なる。

- **ドキュメント（Low-Context）**: 単体で自立して理解できる、現在の正解や仕様
- **モザイク情報（High-Context）**: 個人（作業ログやAIメモリ）や組織（SlackやNotion）に蓄積される、議論の経緯、背景、温度感

仕様が適切にドキュメント化されていれば、モザイク情報は「なぜその決定に至ったのか」を補完する健全な文脈として機能する。

問題は、仕様ドキュメントが存在しない場合に生じる。仕様がドキュメントとして切り出されないと、日々の議論ログやメッセージの中にしか正解が残らない。その結果、本来自立しているべき仕様（Low-Context）と、議論の文脈（High-Context）が未分化のまま混ざり合う。こうして開発者は、文脈の補足ではなく「現在の仕様そのもの」を当てるために、散らばった断片をつなぎ合わせる解読作業を強いられる。

### 3.2 時間軸のフラット化と歴史の喪失

ドキュメントとモザイク情報の間には、更新形式の違いから生じる断絶がある。

ドキュメントは、現在の正解を保つために上書き更新される。一方、SlackやNotion、検索システムに蓄積されるモザイク情報は、追記ログとしてフラットに堆積していく。

この蓄積に対し、キーワード検索やAIのベクトル検索を行うと、情報は時間軸を失い、関連度順にフラットに取り出される。数年前の議論と先週の合意が同列に並ぶため、外部からは因果関係や変更の歴史が判別できなくなる。歴史が失われると、「過去に意図して捨てたはずの設計」を再び提案してしまったり、触れてはならない前提を壊してしまったりする事態を招く。

### 3.3 Gitとモザイクの非対称性

現代の開発において、コードやドキュメントはGitによって時点の再現性を手に入れた。特定のコミットを指定すれば、過去のある時点における状態を厳密に復元できる。

しかし、モザイク情報には、特定の時点の全体像を切り出す仕組みがない。ツールが分断されているため、「コードとドキュメントを半年前の状態に戻したとしても、当時の組織が持っていた前提や文脈（High-Context）を同期して呼び出す」ことはできない。

ドキュメントは履歴をたどれるが過去の文脈を直接は保持せず、モザイク情報は文脈を持つが特定の時点の境界を引けない。この非対称性が、過去の意図の復元をいっそう困難にしている。

## 4. Vibe Management: 曖昧な意図が現場へ流れ込む

情報のモザイクは、既存システムの過去と現在に関する問題である。一方で、開発現場には上流からも曖昧な情報が流れ込む。

要求が曖昧なまま渡される。制約が明確でない。優先順位が共有されない。成功条件が定義されない。何を作らないのかが決まっていない。なぜ今それを作るのかが説明されない。

しかし、納期だけは明確である。

この状態を Vibe Management と呼ぶことができる。

Vibe Management とは、要求、制約、優先順位、判断理由が十分に言語化されないまま、雰囲気、圧力、期限、断片的な情報によって開発を進めようとする管理状態である。

これは単に、マネージャー個人の能力不足を指す言葉ではない。むしろ、意図を言語化し、共有し、検証可能な形にする仕組みが弱い組織で起きる構造的な問題である。

Vibe Management が起きると、開発者は実装者であるだけでは済まなくなる。曖昧な要求を読み解き、背景を推測し、優先順位を補完し、制約を探し、何を作るべきかを自分で判断しなければならない。

つまり、開発者は考古学者であると同時に、要求分析者、翻訳者、リスク評価者、時にはプロダクトマネージャーの代役にもなる。

この負荷は非常に大きい。

しかも、既存システム側がすでにモザイク化している場合、問題はさらに悪化する。開発者は、上流から来る曖昧な要求を、下流にある曖昧な現実へ接続しなければならない。要求も曖昧で、現実も曖昧で、その間をつなぐ意図も記録されていない。

この状態で実装だけを急がせると、推測に基づく判断がコードへ埋め込まれる。その判断が記録されなければ、次の開発者にとっては新しい謎になる。

こうして、Vibe Management は新しいドキュメント・ドリフトと理解負債を生む。

## 5. 技術的負債が考古学をさらに難しくする

ソフトウェア考古学を難しくするもう一つの要因が、技術的負債である。

技術的負債が少ないシステムでは、コードの構造、命名、責務境界、テスト、ドキュメントが比較的一貫している。そのため、情報に多少の欠落があっても、コードやテストから現在の構造を推測しやすい。

しかし、技術的負債が多いシステムでは、この推測が難しくなる。

責務境界が崩れている。命名が実態を表していない。似たような処理が複数箇所に分散している。テストが不足している。コメントが古い。例外処理が複雑に積み重なっている。データモデルが現実の業務概念とズレている。暫定対応が恒久化している。

このような状態では、コードを読んでも、意図を復元しにくい。

コードは「現在どう動いているか」を示す。しかし、その動きが本来の仕様なのか、過去のバグの名残なのか、納期都合の妥協なのか、特定顧客向けの例外なのか、誰も消せなくなった暫定対応なのかは、コードだけでは判断できない。

技術的負債は、変更を難しくするだけではない。理解を難しくする。理解が難しくなると、変更はさらに危険になる。危険な変更は避けられ、周辺に回避策が積み重なる。回避策はさらに構造を複雑にする。

この循環によって、技術的負債と理解負債は互いに強化し合う。

## 6. この作業は高度な実力を要求する

ソフトウェア考古学は、単純な情報検索ではない。

必要なのは、コードを読む力だけではない。ドメイン理解、設計判断、運用知識、組織文脈、過去の意思決定の推定、矛盾情報の扱い、変更影響の見積もり、リスク判断が必要になる。

たとえば、ある仕様書とコードが矛盾しているとする。そのとき、開発者は次のような問いに答えなければならない。

- 仕様書が古いのか
- コードが間違っているのか
- 仕様が変わったのに記録されていないのか
- 特定顧客向けの例外なのか
- バグだが運用で依存されているのか
- テストが現在の仕様を表しているのか
- 今変更するとどこが壊れるのか
- 誰に確認すべきなのか

これらの判断は、経験の浅い開発者には難しい。熟練した開発者であっても、時間がかかる。しかも、組織の文脈を知らなければ正しく判断できないことが多い。

この作業は、しばしば「調査」「キャッチアップ」「既存コード理解」といった軽い言葉で扱われる。しかし実態としては、システムの現在地を復元する高度な知的作業である。

熟練者ほど、この作業を無意識に行っている。どの情報が怪しいか、どのファイルが信頼できるか、誰に聞けばよいか、どの変更が危険かを経験的に判断している。

しかし、無意識にできるからといって、コストが存在しないわけではない。

## 7. コストは個人に内面化され、組織から見えなかった

情報のモザイクとソフトウェア考古学の問題が長く見過ごされてきた理由の一つは、そのコストが個人に内面化されていたからである。

開発者は、古い仕様書を疑い、コードと照合し、人に聞き、過去のIssueを掘り、文脈を推測する。これらは日常業務の中に溶け込んでいる。

組織から見ると、それは単に「調査に時間がかかっている」ように見える。あるいは「この領域は属人化している」「コミュニケーションが足りない」「ドキュメント文化が弱い」と表現される。

しかし、これらは同じ根本問題の異なる見え方である。

問題は、単に調査が遅いことではない。信頼できる情報が一箇所に存在せず、情報空間がモザイク化していることである。

問題は、単に属人化していることではない。属人に頼らなければ現在の真実を復元できない状態になっていることである。

問題は、単にコミュニケーション不足であることではない。意図、判断理由、制約、例外、変更履歴が、共有可能な形で残っていないことである。

このコストは、開発速度を下げるだけではない。レビューを重くし、オンボーディングを難しくし、障害対応を遅らせ、リファクタリングを危険にし、チームの心理的負担を増やす。

そして最も厄介なのは、このコストが可視化されにくいことである。

熟練者が吸収している間は、組織は問題の大きさに気づきにくい。熟練者が離脱したとき、あるいはシステムが大きくなりすぎたとき、初めて問題が表面化する。

## 8. まとめ: 本当のボトルネックは意味の復元にある

ソフトウェア開発の現場では、コードを書く前に、まず意味を復元しなければならないことが多い。

現在の仕様は何か。コードはなぜそうなっているのか。どのドキュメントが正しいのか。どの情報が古いのか。どの判断がまだ有効なのか。どの制約を守るべきなのか。何を変えると危険なのか。

この復元作業は、ドキュメント・ドリフト、情報のモザイク、Vibe Management、技術的負債、理解負債によって難しくなる。

そして、この作業は高度な実力を要求するにもかかわらず、長い間、熟練開発者の暗黙スキルとして扱われてきた。組織はそのコストを正しく測定せず、方法論もこの問題を中心には置いてこなかった。

この問題はAI以前から存在していた、という点が重要である。

AIは、この問題を突然生み出したわけではない。むしろ、すでに存在していたモザイク化した情報空間、失われた意図、曖昧な要求、技術的負債を、より高速に消費し、より大きな影響を持つ形で表面化させる。

次に考えるべきなのは、AIがこの状況に何をもたらすのかである。コード生成のコストが下がったとき、問題は本当に解決するのか。それとも、意味の復元と意図の検証という、これまで熟練者が担ってきた最も難しい作業が、さらに重要になるのか。
