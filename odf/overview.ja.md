# ODF (Orthogonal Dual-Framework) 概要

## 1. はじめに

ODF（Orthogonal Dual-Framework：直交二重フレームワーク）は、ソフトウェア開発ライフサイクル（SDLC）において、明確に異なる2つの独立した仕事を担うフレームワークです。

この2つを1つの図や文脈で同時に説明しようとすると混乱を招くため、ODFでは「仕事1：Proxy」と「仕事2：Environment ⇄ Intent の Lean Loop」に明確に切り分けて定義します。

- **仕事 1：IGE ⇄ ODF ⇄ ISE（Proxyとしての仕事）**  
  PMの世界（IGE）と開発者の世界（ISE）の間に立ち、タスク量や開発速度を調停して現場の健全性を保ちます。
- **仕事 2：Environment ⇄ ODF ⇄ Intent（探索ループとしての仕事）**  
  現実世界（Environment）と頭の中の意図（Intent）を結び、意図をどう実現して価値を検証していくかというLean BML Loopを担当します。

---

## 2. 仕事 1：IGE ⇄ ODF ⇄ ISE（Proxyとしての仕事）

第1の仕事は、PM（IGE）と開発者（ISE）の間を取り持つProxy（代理人・緩衝材）です。

```text
  【 PMの世界 】                                   【 開発者の世界 】
       IGE                                                ISE
(頭の中のIntentの具体化、                         (開発者をAIで助け、
 要求書・機能設計・タスク化)                         IntentとRealityを同期)
       ▲                                                  ▲
       │                                                  │
       │                  +─────────────+                 │
       └────────────────> │     ODF     │ <───────────────┘
                          │   (Proxy)   │
                          +─────────────+
                                 │
                   ・タスク量は適正か？
                   ・開発速度（ベロシティ）は？
                   ・無理な要求をISEに投げていないか？
```

### 1. 現場のキャパシティと開発速度の調停
PM（IGE）は、ビジネスの要請から多くの機能を作りたいと考え、タスクを次々に起票します。しかし、開発側（ISE）の消化速度や認知的キャパシティには限界があります。
ODFはこの間に立ち、タスク量が開発側の消化速度（ベロシティ）と無理なく釣り合っているか、無理な割り込みや要求をISEに直接押し付けて現場を疲弊させていないかを調停します。

### 2. 工学的制約のフィードバック
開発現場（ISE）側からの「この設計は既存アーキテクチャへの影響が大きすぎる」「技術的負債の返済が先である」といった制約や懸念をODFが受け止め、PM側へスコープ縮小や優先順位の見直しを促します。

### 3. 現場における具現化
このProxy機能は、GitHubのIssueやプルリクエスト、スプリントバックログ、RFCレビュープロセスなどとして具現化されます。

---

## 3. 仕事 2：Environment ⇄ ODF ⇄ Intent（Lean Loopとしての仕事）

第2の仕事は、不確実な現実世界（Environment）と頭の中の意図（Intent）を結び、意図をどう実現して価値を検証していくかという探索ループ（Lean Loop）を回すことです。

```text
               [ Environment (市場・顧客・ビジネスの現実) ]
                                     ▲
                                     │
                             BML Loop (Lean)
                       ・どう実現し、価値を検証するか
                       ・計測結果から環境認識を改める
                                     ▼
                              +-------------+
                              |     ODF     |
                              +-------------+
                                     ▲
                                     │
                                     ▼
                 [ Intent (人の頭の中にのみ存在する意図) ]
                                     ▲
                                     │ 要求工学 (RE)
                                     │ (頭の中の意図を要求書として外部化)
                                     ▼
                         [ Document (要求書・仕様書) ]
```

### 1. なぜLean Loopが必要なのか
新機能や施策がビジネス的に狙いどおり当たるかどうかは、事前には分かりません。機能を作っても誰も使わなかったという事態は日常的に起こります。
そのため、頭の中の意図をいきなり巨大な完成品として作り込むのではなく、小さくBuildし、Measure（計測）し、Learn（学習）して環境に対する認識を改めるLean BML Loopが不可欠です。

### 2. 要求工学（RE）とLeanの役割分担
ここにおける要求工学とLeanは、対象とする境界が異なります。
- **要求工学の担当領域（Intent ⇄ Document）**  
  人の頭の中にある曖昧なIntentから要求書（Document）を起こし、機能設計や受け入れ基準へと具体化・言語化する部分です（主にIGEが実務を担います）。
- **Leanの担当領域（Environment ⇄ ODF ⇄ Intentの大ループ）**  
  具体化されたIntentをどう現実（Reality）にぶつけて実現し、価値を検証していくかという大きなサイクル全体を推進します。

### 3. 計測（Measure）と学習（Learn）の還流
本番環境（Reality）にテレメトリやログの観測点を埋め込み、データを計測・収集するのは実装側（ISE）の仕事です。
ISEが計測した結果を受けて、環境に対する理解そのものを改め、仮説（Intent）を更新・改訂・棄却（Learn）するのがODFの仕事です。使われない機能であれば、ODFはその学びからIntentを取り下げ、機能をコードから綺麗に削ぎ落とす判断を下します。

---

## 4. まとめ

ODFは、次の2つの独立した仕事の統合です。

1. **Proxy軸（IGE ⇄ ODF ⇄ ISE）**  
   PMと開発者の間に立ち、タスク量や開発速度を調停して現場の崩壊を防ぎます。
2. **Lean Loop軸（Environment ⇄ ODF ⇄ Intent）**  
   要求工学によってドキュメント化されたIntentを、どう実現して価値を確かめるかというBML大ループを統制し、計測データから環境認識を改め続けます。
