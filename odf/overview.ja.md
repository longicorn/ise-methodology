# ODF (Orthogonal Dual-Framework) 概要

## 1. はじめに

ODF（Orthogonal Dual-Framework：直交二重フレームワーク）は、ソフトウェア開発ライフサイクル（SDLC）における二つの直交する境界に、同じProxyの原理を適用するフレームワークです。

二つの軸は調停する境界が異なるものの、独立した別々の仕事ではありません。どちらの軸でも、ODFは一方から得た情報を解釈して判断を媒介し、境界の反対側へフィードバックを伝えます。

なお、ODFは単なる緩衝材ではありません。ISEやIGEの外側にあるプロダクト全体（アーキテクトや経営層に近い領域）を担う立場から、二つの境界を調停します。そのため、他のフレームワークに比べて責務は重くなります。

- **Proxy軸 1：IGE ⇄ ODF ⇄ ISE（開発運用の調停）**
  PM（IGE）と開発者（ISE）の間で、要求、タスク量、開発能力、工学的制約を調停します。
- **Proxy軸 2：Environment ⇄ ODF ⇄ Intent（Lean Loopによる探索の調停）**
  外部のEnvironmentと人のIntentの間で、証拠と仮説をLean BML Loopを通じて媒介し、現実に照らして意図を検証・更新します。

---

## 2. Proxy軸 1：IGE ⇄ ODF ⇄ ISE（開発運用の調停）

この軸では、ODFはPM（IGE）と開発者（ISE）の間を取り持つProxy（代理人・緩衝材）として働きます。

```text
  【 PMの世界 】                                   【 開発者の世界 】
       IGE                                                ISE
(頭の中のIntentの具体化、                         (開発者をAIで助け、
 要求書・機能設計・タスク化)                         IntentとRealityを同期)
       ▲                                                  ▲
       │                                                  │
       │                  +─────────────+                 │
       └────────────────> │     ODF     │ <───────────────┘
                          │   (Proxy)   │
                          +─────────────+
                                 │
                   ・タスク量は適正か？
                   ・開発速度（ベロシティ）は？
                   ・無理な要求をISEに投げていないか？
```

### 1. 現場のキャパシティと開発速度の調停
PM（IGE）は、ビジネスの要請から多くの機能を作りたいと考え、タスクを次々に起票します。しかし、開発側（ISE）の消化速度や認知的キャパシティには限界があります。
ODFはこの間に立ち、タスク量が開発側の消化速度（ベロシティ）と無理なく釣り合っているか、無理な割り込みや要求をISEに直接押し付けて現場を疲弊させていないかを調停します。

### 2. 工学的制約のフィードバック
開発現場（ISE）側からの「この設計は既存アーキテクチャへの影響が大きすぎる」「技術的負債の返済が先である」といった制約や懸念をODFが受け止め、PM側へスコープ縮小や優先順位の見直しを促します。

### 3. 現場における具現化
このProxy機能は、GitHubのIssueやプルリクエスト、スプリントバックログ、RFCレビュープロセスなどとして具現化されます。

## 3. Proxy軸 2：Environment ⇄ ODF ⇄ Intent（Lean Loopによる探索の調停）

この軸では、ODFが不確実なEnvironmentと人のIntentの間に立ち、Lean Loopを通じて証拠と仮説を往復させ、意図の実現方法と価値を検証します。

```text
               [ Environment (外部世界・運用環境・市場) ]
                                     ▲
                                     │
                             BML Loop (Lean)
                       ・どう実現し、価値を検証するか
                       ・計測結果から環境認識を改める
                                     ▼
                              +-------------+
                              |     ODF     |
                              +-------------+
                                     ▲
                                     │
                                     ▼
                 [ Intent (人の頭の中にのみ存在する意図) ]
                                     ▲
                                     │ 要求工学 (RE)・実験設計
                                     │ (頭の中の意図を要求書・検証計画として外部化)
                                     ▼
                         [ Document (要求書・仕様書) ]
```

### 1. 説明にLean BML Loopを用いる理由
新機能や施策が外部環境において意図どおりに効果を上げるかは、事前には分かりません。機能を作ったものの、実際には使われなかったり、予期せぬ摩擦を生んだりする例は、ビジネスに限らずあらゆるソフトウェア開発で日常的に生じます。
この流れを説明するため、本稿ではLean BML Loopを例として用います。Leanはその実現方法の一つであり、ODFやIGEの役割をLeanに限定するものではありません。将来、より適した方法があれば、置き換えたり組み合わせたりできます。

### 2. 要求工学（RE）とLeanの役割分担（ODF・IGE・ISEの連携）
ここにおける探索サイクルは、3つのフレームワークが次のように直交・連携して回します。

- **ODF（環境理解と探索の調停 / Environment ⇄ ODF ⇄ Intent）**
  環境の変化や計測結果をもとにEnvironmentへの理解を深め、探索の問いを整えます。
- **IGE（Intent・実験・計測要件の具体化 / Intent ⇄ Document）**
  ODFの環境理解を受け、検証可能なIntent、実験計画、計測要件へと具体化します。
- **ISE（Realityへの実装 / Intent ⇄ Reality）**
  合意されたIntentと実験計画を仕様・コード・テスト・運用に反映し、必要な観測点を実装します。

計測結果を受けたIntentの更新・棄却や機能の廃止は、課題の範囲や判断の文脈に応じてODFまたはIGEが担います。実装物やコードの変更・削除は、決定されたIntentをRealityへ反映するISEが実行します。

### 3. グッドハートの法則と「Metric as Sensor」
探索サイクルを考える際の参考となる視点の一つが、「**測定値が目標になった瞬間、それは良い測定値ではなくなる（グッドハートの法則）**」です。

計測要件は、検証のために何を観測するかを定めるもので、メトリクスを達成目標にすることを意味しません。メトリクスを目標や絶対的な真実と同一視すると、数値を改善することが目的化し、意図やシステム全体を損なう場合があります（例：強引なCVR改善や、意味の薄いテストでカバレッジを上げること）。

メトリクスは、環境の変化やシステムの状態を知る手がかり、つまりセンサーとして捉えることができます。ODFが環境を理解する際に、単一の数値だけで判断せず、他の証拠やシステム全体の状況と合わせて解釈する方法も有効です。

ここでの担当はLean BML Loop全体を調停する立場からの整理です。学びを受けてIntentを改訂・棄却する判断は、全体の環境理解に関わる場合はODF、個別の仮説や実験に関わる場合はIGEが担うなど、状況に応じて決めます。ISEは決定を受けてReality上の成果物を変更します。詳しくは[概要](../overview.ja.md)の「3. SDLCにおける3つの抽象化フレームワーク」を参照してください。

---

## 4. まとめ

ODFは、同じProxyの原理を次の二つの直交する軸に適用します。

1. **開発運用の調停（IGE ⇄ ODF ⇄ ISE）**
   PMと開発者の間で要求、タスク量、開発能力、工学的制約を調停します。
2. **探索の調停（Environment ⇄ ODF ⇄ Intent）**
   Lean Loopを通じて証拠と仮説を媒介し、Intentを現実に照らして検証・更新します。
